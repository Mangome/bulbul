## Context

当前省份地理过滤流程：用户选择省份 → 传递省会坐标 `(lat, lng)` → `query_local_species` 用 `floor()` 取整查询单个 1°×1° 网格 → 返回该网格的物种列表用于过滤。

核心问题：一个省的实际范围通常是 5°~10° 的跨度（如新疆跨约 16°×20°），而当前只查了省会所在的 1 个网格，遗漏了 80-99% 的省内网格，大量本省有分布的鸟种被错误过滤。

现有架构约束：
- 网格数据 `species_grid_1deg.json.gz` 为 1° 分辨率，格式不可变
- 前后端通过 Tauri IPC 通信，需同步修改接口签名
- settings.json 已有旧版 Province 格式（只有 name/lat/lng），需兼容

## Goals / Non-Goals

**Goals:**
- 选择省份后，查询该省边界框内所有网格的物种并集，覆盖省内所有鸟种
- 最小化改动范围：复用现有网格数据，不引入新数据源
- 前后端接口变更平滑，兼容旧版 settings 数据

**Non-Goals:**
- 不引入省份多边形精确边界（矩形边界框精度足够，鸟类分布本身是渐变的）
- 不修改网格数据格式或分辨率
- 不修改前端省份选择器的 UI 交互
- 不处理"用户拍照位置在省边缘但靠近邻省"的精细场景（宁多勿漏策略）

## Decisions

### Decision 1：Province 数据结构扩展为边界框

在 `Province` 接口中新增 `minLat, maxLat, minLng, maxLng` 四个字段，保留原有 `lat, lng` 作为省会坐标（仍可用于 UI 显示和默认值）。

**为什么不用"半径"方案**：圆形对狭长省份（甘肃 ~15°×4°、内蒙古 ~15°×10°）拟合极差，要么角落覆盖不足，要么大部分区域冗余。矩形边界框与省级行政区形状更匹配。

**为什么不用预计算省份物种表**：虽然运行时更快（O(1) 查表），但需要离线生成脚本和维护额外数据文件。边界框方案在运行时查询多格的并集，34 个省平均 ~30 个网格，HashSet 并集操作微秒级完成，性能完全可接受。

### Decision 2：后端 `reclassify` / `process_folder` 接口改为传递边界框

IPC 接口从 `(lat, lng)` 改为 `(minLat, maxLat, minLng, maxLng)`。后端内部使用边界框查询物种并集。

**为什么不在前端做并集查询**：geo_filter 逻辑和网格数据都在 Rust 侧，前端只传参数不涉及数据。

**接口设计**：
- `reclassify(min_lat, max_lat, min_lng, max_lng)` — 4 个 f64 参数
- `process_folder(..., min_lat, max_lat, min_lng, max_lng)` — 扩展可选参数
- 清除省份时传 `(0, 0, 0, 0)` 表示不应用地理过滤（与当前 `lat=0, lng=0` 语义一致）

### Decision 3：后端新增 `query_local_species_in_bbox` 函数

在 `geo_filter.rs` 中新增函数，遍历边界框内所有网格 key，取物种并集。保留原 `query_local_species` 不变（单点查询仍有独立价值，如默认 GPS 坐标场景）。

### Decision 4：settings.json 兼容旧格式

`settingsStorage.ts` 的 `isValidProvince` 校验函数：当旧数据缺少边界框字段时，用省会坐标推算默认边界框（±2°），确保旧数据不丢失。

## Risks / Trade-offs

- **[边界框角落多覆盖邻省物种]** → 可接受。鸟类过滤策略是"宁多勿漏"：多保留几个物种只是概率不被压制，漏掉则直接置零。邻省物种被保留不会导致误识别，只是过滤宽松度略增。
- **[边界框数据精度依赖人工整理]** → 34 个省份的经纬度范围是公开地理数据，来源可靠。数据量小（34×4 个数字），可逐条核实。
- **[多网格查询增加运行时开销]** → 平均每个省 ~30 个网格的 HashSet 并集操作，实测在微秒级，相比模型推理的毫秒级开销可忽略。
- **[IPC 接口签名变更]** → 前后端同步修改，无中间版本兼容问题（Tauri 桌面应用统一发布）。
